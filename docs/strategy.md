# 换钥策略：原地逐块 vs 影子副本

本工作台只实现了 **原地逐块**。影子副本的取舍写在这里，供决策时对照，不提供半成品实现——一个没做写屏障/对账的影子切换，看起来能跑，却会在切换窗口里丢写，比不做更危险。

## 约束回顾

- 部分列加密：`customer_email`(pii)、`session_label`(analytics)、`audit_ref`(audit)。
- 换钥期间**查询和新写入必须继续**。
- 读者可能同时遇到**两代密文**。
- 不同用途的密钥绝不混用；密文信封里绑定 purpose，用错用途会直接失败。
- 一次失败不能让明文落到临时文件或错误页。
- 换到一半停进程，重启后能恢复。
- 旧查询还在读时不能销毁所需密钥；用途撤销后旧缓存不能再出值。

## 方案 A：原地逐块（已实现）

**顺序**：先启用新钥（写路径立即切到新钥）→ 再从 id 游标逐块把旧行重加密到新钥 → 全表校验 → 删除备份 → 销毁旧钥。

| 维度 | 说明 |
| --- | --- |
| 写入连续性 | 切钥瞬间起，所有新写入用新钥；无需停写，无需双写。 |
| 每块原子性 | 每块一个 `BEGIN IMMEDIATE` 事务：备份镜像 + 该列更新 + 游标推进一起提交，崩溃只会回到上一块边界。 |
| 读取连续性 | 读路径按信封里的钥 id 选密钥，新旧两代同时可读；旧钥在退休期仍可解密。 |
| 空间 | 备份表只存**已迁移行的 id 与被迁移的那一列**（不是整行），峰值约为该列已迁移部分，外加 SQLite WAL。可迁移一块、校验一块后增量丢弃备份，但那样会失去整表回滚。本工作台保留到显式删除。 |
| 回滚 | 从备份表按 id 反向恢复。并发改写过的行用写入指纹识别，记为冲突并保留现值，绝不覆盖无法证明属于本任务的数据。 |
| 中断恢复 | 游标在库里；重启后任务被标记 `interrupted`，从游标继续或从备份回滚。 |
| 主要风险 | 迁移期间的写放大与长事务；备份表期间占空间；必须校验才能确认没有旧钥漏网。 |
| 适用 | 单库、可接受一份额外空间、要求轮换窗口内持续读写。 |

关键实现细节：

- 每块只碰 `id > cursor` 的行；已经在目标钥下的行直接跳过。切换写路径发生在回填之前，所以并发写入不会在游标后面留下旧钥行。
- 不认识的钥 id（既非源也非目标）立即报错并整块回滚，**不猜**。
- 校验阶段逐行检查钥 id 与 GCM 认证；任何旧钥行都计为校验错误，任务转 `failed`。
- 备份里的旧钥密文会阻止旧钥销毁——否则回滚将不可能。备份按任务限定列：pii 轮换的备份只含 `customer_email`，不会把 analytics 的旧钥密文抄进去，因此不会错误地钉住别的用途的旧钥。

## 方案 B：影子副本切换（未实现，设计对照）

**顺序**：建影子表 → 双写原表与影子表（或用触发器/写屏障保证不漏写）→ 回填影子表 → 校验 → 原子换名 → 观察期后删旧表。

| 维度 | 说明 |
| --- | --- |
| 写入连续性 | 需要双写或写屏障；双写失败要有补偿与对账，否则切表后丢最近写入。 |
| 空间 | 约 **2 倍表**（原表 + 影子表）再加索引；比 A 更贵。 |
| 回滚 | 换名前只需丢弃影子表，原表未动，最安全；换名后回滚要换回旧表。 |
| 中断恢复 | 回填阶段中断只需删影子表重来；**换名窗口**需要一小段停写或元数据锁。 |
| 主要风险 | 双写一致性、换名瞬间的锁与流量尖峰、对账窗口、两倍空间。 |
| 适用 | 能接受短暂停写、空间充足、希望"换名前零风险"的场景。 |

### 选择规则（可操作）

- 只要"轮换窗口内绝不能停写"且希望流程单向可续 → 选 **A**，并确保有备份表空间与校验步骤。
- 若能安排几十秒维护窗口、且更看重"换名前旧表完全不动" → 选 **B**，但必须先有双写/写屏障与对账，否则不要上线。
- 两者都必须满足同一组旧钥退出条件（见下）；**销毁密钥永远在最后一步**。

## 旧钥退出条件（本工作台强制）

旧钥（`retiring`）只有在下列全部成立时才能销毁，检查在同一个 `BEGIN IMMEDIATE` 事务里完成：

1. 活跃表 `events` 中该用途列没有该钥 id 的密文；
2. 属于同一用途列的 `events_backup_*`，以及所有 `events_shadow_*`，没有该钥 id 的密文（否则无法回滚）；
3. 没有活动查询/迁移租约指向该钥或该用途；
4. 退休后静默期（`REKEY_GRACE_SECONDS`）已过；
5. 没有以该钥为源或目标的未终结任务（`running/paused/interrupted/verifying/rolling_back/rollback_interrupted/failed`）。

因此顺序总是：**校验通过 → 删除备份 → 等静默期 → 确认无租约 → 销毁**。销毁后 `loadKeyForRead` 一律拒绝，缓存按钥 id 失效。

## 用途撤销的语义

- 撤销（revoke）立即：清空该用途内存缓存、拒绝新读取、拒绝新写入、拒绝为该用途启动轮换。
- 撤销**不**强行中断已在进行中的读租约：一次已开始的读取可以完成，但之后任何读取都拿不到值，缓存也不会再出值。
- 密文仍在盘中但不可解；恢复用途后才可再次读取。这避免"撤销即丢数据"的误操作。

## 恢复与空间小结

| 场景 | 原地逐块 A | 影子副本 B |
| --- | --- | --- |
| 迁移中途 kill -9 | 从游标继续；无需重跑已提交块 | 删影子重来（回填阶段零风险） |
| 迁移完成后发现问题 | 从备份回滚（冲突行保留现值） | 换名前丢影子；换名后换回旧表 |
| 额外空间峰值 | ≈ 已迁移行备份 + WAL | ≈ 整表 1 倍 |
| 旧钥最早可销毁 | 校验通过 + 删备份 + 静默期 + 无租约 | 换名稳定 + 观察期 + 无租约 |

## 明确不做的事

- 不自创加密算法：只用 AES-256-GCM（`node:crypto`），AAD 绑定 version/purpose/keyId/rowId/column。
- 不接真实 KMS/HSM；本地测试钥以 0600 文件存放，仅供演示。
- 不把明文写入磁盘缓存或临时文件；缓存只在进程内存。
- 不实现影子策略的"半套"版本。
